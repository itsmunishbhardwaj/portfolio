Approach

Implemented Azure Workload Identity end to end — 24 federated credentials across 11 namespaces, 13 managed identities per environment, scoped per workload rather than shared.

Per-agent, per-tenant identity with least-privilege scopes; secrets that rotate without a redeploy; every credential attributable to the action it authorized.

Result

An agent's permissions become a thing an operator can inspect and revoke, not a thing they have to trust.

So what: the first time an agent sends something on the company's behalf, the only question that matters is what it was allowed to do — and who can prove it.

Challenge

An assessment tool where the same answer had to produce the same diagnosis every time. Letting the model classify meant the verdict drifted between runs — unusable for anything anyone relies on.

Approach

Took classification away from the model. Headline scores and gap type are computed deterministically in Python from locked thresholds; the LLM only writes the narrative around a verdict the code has already fixed. The same problem at ZenSpace
Challenge

A Pricing Agent that moves a rate and a Distribution Agent that syncs inventory cannot be non-deterministic about the decision itself. An operator will accept an agent that explains a rate change; they will not accept one that gives two different answers to the same day.

Approach

Draw the line explicitly: the yield logic, the bounds check and the eligibility rules are code; the model writes the explanation and handles the messy natural-language edges. Model routed by job rather than one model everywhere, with cost per decision tracked from day one.

Recommend → Permission → AutomateYour trust ladder, with a delivery plan attached.

ZenAI's own three rules are recommendation mode by default, permissioned actions, and an audit log on everything. That's not just a product principle — it's a build order. Here's how I'd run it.

PHASE 01 · DAYS 1—30

Recommend

Make every agent observable before it's clever

Objective

Get all four agents producing recommendations against real property data, with every suggestion logged, scored and reviewable — and nothing acting yet.

Key activities

  • Instrument the agent loop end to end: inputs, retrieved context, prompt version, output, latency, cost.
  • Stand up the eval harness with golden cases per agent, drawn from real property history.
  • Map every write path an agent could eventually take, and gate it behind a flag.

Deliverable

Agent observability dashboard plus a versioned eval suite running in CI.

Success: 100% of agent recommendations traceable to their inputs, with a weekly accuracy number an operator can read.
PHASE 02 · DAYS 31—60

Permission

Draw the box before anything moves inside it

Objective

Ship the guardrail layer — scoped credentials, price bounds, channel whitelists, approval queues — so the first automated action happens inside limits an operator set themselves.

Key activities

  • Per-agent, per-tenant identity with least-privilege scopes across PMS, channels, payments and locks.
  • Human-in-the-loop approval flow with durable state, so a pending action survives a restart.
  • Immutable audit log with a defined undo path per action class.

Deliverable

Guardrail configuration as code, per property, diffable and reviewable.

Success: zero agent actions outside operator-defined bounds, and every action reversible in one step.
PHASE 03 · DAYS 61—90

Automate

Promote on evidence, one behavior at a time

Objective

Move the first agent behaviors from recommend to act at launch-partner properties, using the eval pass rate as the promotion criterion — not the calendar.

Key activities

  • Define the trust threshold per behavior and promote only what clears it.
  • Harden the retrieval and memory layer so agents answer from what the business actually knows.
  • Write the runbooks and hand the controls to the ops team.

Deliverable

Launch-partner properties running automated behaviors with monitoring and rollback in place.

Success: measured lift on the promoted behaviors, no unattributed agent action, and a documented path for the next one.

The honest version

Why an infrastructure engineeris applying for a founding AI role.

The short version: I've spent six years on the least glamorous part of software, and the agent industry is about to discover it needs that part badly.

Most of what I read about agents is about capability — longer context, better tools, cleverer planning. Almost none of it is about the question an operator actually asks before switching one on: what happens when it's wrong, who finds out, and how fast can we undo it. That question is my entire professional background. I've answered it for TD Bank, for CBA, for Snowflake, in environments where the answer had to survive an audit.

So I started building, and then I started shipping. An LLM test report generator into H2O.ai's CI, with every generated claim cited back to a real test run. Seventeen-plus skills that made our QA lifecycle executable in plain English. Gauge, deployed and public, where I learned the lesson that shows up everywhere on this page: take the decision away from the model, let it write the explanation, and the system becomes something an operator can actually trust.

What I haven't done is own the whole stack at once — memory layer, integrations, evals and product features as a single system with my name on it. That's an ownership gap rather than a knowledge gap, and it's the specific thing this role offers. Everything underneath it, I've been doing for six years: distributed, stateful systems acting on real infrastructure, expensive when wrong. My job has been to make that boring, which in this line of work is the highest compliment available.

What I bring on day one

  • Six years of production ownership across AWS, Azure and GCP, for clients who audit everything.
  • A testing and evaluation instinct built on 1,600 test functions and 198 specs, not on theory.
  • Identity and secrets done properly — the difference between an agent that's permissioned and one that's merely convenient.
  • Documentation as a reflex: 34 technical docs including an 812-line debugging guide, so a small team isn't dependent on me.
  • Comfort at small-company pace — I scope, build, ship and then maintain the thing I shipped.
  • LLM tooling already shipped inside an engineering org, plus a deployed public app — and no interest in overstating any of it.

The hard part of agents was never making them capable. It's making them accountable — permissioned, measured, and reversible — and that's an infrastructure problem the industry hasn't finished solving yet.
