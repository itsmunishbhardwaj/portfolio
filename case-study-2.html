Four Options, One Decision: Isolating a Production Cluster

Airgapping a production OpenShift cluster — and choosing the boring option on purpose.

Before → After

Before: Open cluster, shared blast radius

No network isolation boundary on a QA-priority ROSA cluster.

The "obvious" tool (AWS Network Firewall) would have made this cluster's firewall the control plane for all 6 clusters in the account.

After: Scoped isolation, matched to the constraint

AWS Security Groups enforcing the boundary — implemented, not just proposed.

Isolation scoped to this cluster only, zero shared blast radius introduced.

The Problem

Every obvious option had a hidden cost

6Clusters in the same AWS account — any shared firewall becomes everyone's dependency
20+Namespaces — per-namespace firewall policy is unmanageable at that scale
4Isolation approaches on the table, each with a real cost
0Of the "obvious" options fit without a hidden trade-off

"I spent the last few days working on airgapping the ROSA cluster." — reporting findings to Joby, Satish, and Jeffrey, Mar 23 2026

The Solution

Four evaluated, one selected for the right reason

  • AWS Network Firewall — rejected: becomes the shared control-plane firewall for all 6 clusters in the account. Wrong blast radius.
  • EgressFirewall (OVN-Kubernetes) — rejected: needs a policy per namespace across 20+ namespaces. Unmanageable at scale.
  • AdminNetworkPolicy / BaselineAdminNetworkPolicy — rejected: not yet part of the ROSA integration surface. Not production-ready here.
  • AWS Security Groups — selected: fastest to implement, smallest footprint, met the actual QA-priority requirement. Matched the real constraint.
The best tool on paper is wrong if it doesn't match your blast radius.
The Impact
1Isolation boundary shipped

Key Learnings
1

Powerful and correct aren't the same thing.

Network Firewall is the more capable product. It was still the wrong choice, because "capable" here meant "becomes a shared dependency for 5 clusters you don't own."

2

Write down what you rejected, not just what you shipped.

The 3 rejected options are as useful to the next engineer as the 1 that got picked — they prevent the same evaluation from being redone from scratch.

3

QA-priority infrastructure needs correctly-scoped tooling, not enterprise-grade tooling.

Matching the solution to the actual stakes is a judgment call, not a technical one.
